# WHAT A SIGN-OUT ACTUALLY COSTS — derived by reading, not measured here.
#
# 513 is the cost of ONE logical removeItem. A sign-out is not one
# logical removal. Pinned auth-js 2.112.3 `_removeSession()`
# (GoTrueClient.js:4389-4405) issues, through THIS adapter:
#   1        removeItemAsync(storage, storageKey)
#   0..5     removeAllPKCEVerifiers -> one per indexed PKCE flow
#            (PKCE_MAX_CONCURRENT_FLOWS = 5, constants.js:50)
#   1        the PKCE flow index key
#   1        the legacy `-code-verifier` key
#   1        `${storageKey}-user`
# `userStorage` is not configured here, so its branch does not run.
# That is 4 to 9 logical removals, and this adapter sweeps the full key
# space on EVERY one of them regardless of what is stored there
# (INVARIANT 3, removeItemBody) — so a sign-out costs
#   2052 to 4617 backend deletes, not 513.
#
# The cycle-2 record said 513 was `paid once per sign-out`. REVIEW-021
# finding 5 caught it and it was wrong by roughly an order of magnitude.
# This block is DERIVED FROM LIBRARY SOURCE at a pinned version, not
# observed: no sign-out has been executed against a real store. It is
# stated as a derivation so it can be checked by reading the same lines.

# WHAT THIS DOES NOT SHOW.
# There is no finite ceiling that is provably unreachable: UserMetadata is an
# open-ended index signature, so for ANY bound a structurally valid session
# above it exists — the 1 MiB row is one. MAX_CHUNKS is a RESOURCE BOUND ON
# REMOVAL, not a safety property, and the refusal above it is a disclosed
# functional limit. What makes that limit safe rather than merely bounded is
# that exceeding it throws BEFORE any backend write: zero writes, a byte-stable
# key set, and the previous value still readable. It never truncates.
#
# Whether the Noema Supabase project would ever return metadata approaching
# this size is NOT RUN — Phase A makes no live auth call. ADR-007 Phase B is
# where a real session is first measured.
