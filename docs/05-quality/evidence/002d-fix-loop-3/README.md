## The negative control — finding 1

`negative-control.sh` proves the gate's exit status from both sides, using the
gate itself, unmodified:

1. a marker line is appended to one gated artifact (`typecheck.txt`) and
   staged, so the index copy no longer matches what regeneration produces;
2. the full gate runs — it reports that artifact `DIFFERS`, and its **process
   exit status is 1**;
3. the artifact and index are restored byte-exactly;
4. the full gate runs again — all gated artifacts `identical`, **process exit
   status 0**.

The transcript keeps the per-artifact status lines, the counts line, the
encoded exit-code line, and the real process exit of each run. The gate's
inline diff hunks are dropped because `diff -u` headers carry mktemp paths and
timestamps.

`negative-control.txt` is reproducible: at the committed head a rerun of
`negative-control.sh` regenerates it byte for byte. It is **not added to the
gated set**, for a structural reason rather than a stability one: the gate
cannot contain a run of itself, and the control temporarily modifies the
index, which the gate must be able to trust. The same applies to the script's
prerequisite that everything be staged.

The controlled artifact is `typecheck.txt` because `capture.sh` regenerates it
from `tsc`'s output — the injected marker cannot leak into the regenerated
bytes, so the injection can only be seen by the comparison, never absorbed.

One recovery note, stated rather than discovered later: the script restores
the artifact and the index itself on its normal path, as the transcript's
closing lines record, but if a run is interrupted between the injection and
the restore, the marker is left in the controlled artifact's working copy and
index. At a committed head the pristine bytes are the committed ones, so
`git checkout HEAD -- docs/05-quality/evidence/002b-fix-loop/typecheck.txt`
recovers both exactly.

## The install transcript — finding 2

`npm-ci.txt` is classified **run-varying**, the same class and for the same
reasons as `../002b-fix-loop/npm-audit.txt`: npm prints deprecation notices in
download-completion order, and the closing audit summary is the upstream
advisory database's answer on the day of the run. The single normalisation is
the wall-clock duration npm appends to its `added …` summary line, masked to
`<duration>` — it measures the machine, not the lockfile. What the OPERATIONS
row claims is
carried by the stable part: the package count, which comes from the committed
lockfile, and the exit code.

**One disclosed retry.** The first run of `npm-ci.sh` in this loop failed with
`ENOTEMPTY: directory not empty, rmdir 'node_modules/@jest'` — npm racing
something else on the machine while deleting the old tree, exit 190. That is
an environmental failure of the same class as the reviewer's sandbox failures
in REVIEW-005: it says nothing about the lockfile. `node_modules` was removed
and the script rerun unchanged; the committed transcript is that second run,
complete with its exit code. The failed transcript is disclosed here rather
than committed, because the claim under test is "the committed lockfile
installs", and it does — the artifact records the install, this paragraph
records the retry.
