# ADR-006: The session adapter detects corruption, and does not claim tamper resistance

**Date:** 2026-08-24
**Status:** Accepted
**Deciders:** Ahmed (owner); CTRL-005 controller

> Immutable. Once committed, do not edit this file. To change the decision,
> write a new ADR and set this one's status to Superseded.

## Relationship to ADR-004

This ADR narrows exactly one sentence of ADR-004, which reads:

> a partial or corrupt read **fails closed to null** rather than handing a
> truncated string to `supabase-js`

Everything else in ADR-004 stands: email one-time code as the v1 auth method,
SecureStore with chunking over AsyncStorage, deterministic chunk keys, complete
cleanup on removal, `localStorage` on web, and the token-opacity constraint.
ADR-004's status remains `Accepted` and its file is not edited — see ruling 16
for why a partial narrowing does not mark the earlier record superseded.

## Context

REVIEW-019 finding 5 demonstrated that the sentence above is unqualified in a
way the implementation cannot satisfy. Two counterexamples were reproduced
deterministically against `d6dc677`:

1. Rewriting the index to a self-consistent `{ __scs: 1, g, n: 1, len }` made
   `getItem` return chunk 0 as a non-null truncated prefix.
2. Altering a chunk without changing total length returned the corrupted string.

The candidate's evidence README disclosed that length is not integrity. The
reviewer correctly held that a disclosure does not narrow an accepted ADR — an
immutable record cannot be amended by commentary elsewhere. Either the
implementation rises to the sentence, or the sentence is replaced. This ADR
replaces it, and requires the implementation to rise most of the way.

The constraint on the remedy comes from ADR-004 itself, which names the adapter
as custom code in the highest-risk position in the codebase. A cryptographic
digest would put a crypto dependency on the auth path, which is precisely the
surface ADR-004 sought to keep minimal.

## Decision

A read **fails closed to `null`** when the index is missing, unparseable, or out
of range; when chunk count or total length disagrees with the index; **or when a
non-cryptographic checksum recorded in the index disagrees with the reassembled
payload**. The checksum is computed inline, adds no dependency, and uses no
cryptographic API.

It is **corruption detection, not tamper resistance.** It catches truncation,
accidental damage, and the interleaved-writer hybrid that REVIEW-019 finding 2
reproduced. It does not resist an adversary who can write arbitrary
self-consistent values into the Keychain or Keystore, and no claim to the
contrary may be made in evidence, documentation, or product copy.

## Alternatives considered

| Option | Why not |
|---|---|
| Subtraction alone — narrow the ADR, add no checksum | Defensible on threat model: an attacker who can rewrite a self-consistent index already holds the tokens, so the container is not defensible from inside. Rejected because it leaves the finding-2 hybrid resting entirely on writer serialization being perfect, and this unit has already failed to land that property once. The checksum is independent defence in depth against a bug, not only against an attacker. |
| Cryptographic digest (SHA-256 via `expo-crypto`) | Real integrity, but adds a dependency and a crypto call on the auth path against ADR-004's explicit minimality constraint — while still not resisting an adversary who can recompute the digest. Cost without the corresponding gain. |
| Leave ADR-004 unqualified and treat finding 5 as an implementation defect to be fully fixed | The unqualified sentence is not satisfiable at this layer at any reasonable cost. Keeping it would guarantee a permanently open finding, or a claim the architecture does not enforce — the exact failure principle 4 exists to prevent. |

## Consequences

- The adapter gains a checksum field in its index and a verification step on
  read. Small, dependency-free, and inside code that is already being reworked
  under fix cycle 1.
- The evidence suite must state the corruption-detection/tamper-resistance
  distinction explicitly. A claim of tamper resistance is barred.
- Reads now fail closed on same-length corruption and on self-consistent index
  forgery where the payload does not match its recorded checksum — closing both
  REVIEW-019 finding 5 counterexamples.
- Recorded as binding ruling 15 in `PROJECT-STATE.md` in this same commit. The
  partial-supersession mechanic used here is recorded as ruling 16.
- This is the client auth surface; every future change to it remains RED lane.
