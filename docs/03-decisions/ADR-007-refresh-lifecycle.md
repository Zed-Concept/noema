# ADR-007: The auth client never self-schedules a refresh

**Date:** 2026-08-24
**Status:** Accepted
**Deciders:** Ahmed (owner); CTRL-005 controller

> Immutable. Once committed, do not edit this file. To change the decision,
> write a new ADR and set this one's status to Superseded.

## Relationship to ADR-005

This ADR narrows exactly one sentence of ADR-005:

> Token auto-refresh is **gated on AppState** [...] so a refresh only ever
> fires while the app is foreground and the device therefore unlocked.

ADR-005's other decisions stand unchanged: `signOut()` passes `scope: 'local'`,
SecureStore keeps `WHEN_UNLOCKED`, and there is no remote revocation until a
"sign out everywhere" affordance exists. ADR-005's status remains `Accepted`
and its file is not edited — ruling 16.

## Context

REVIEW-020 finding 1 established with three deterministic probes against pinned
`@supabase/auth-js` 2.112.3 that the narrowed sentence cannot be enforced while
the client schedules its own refreshes:

1. Client construction with `autoRefreshToken: true` begins `_initialize()`,
   which recovers the stored session and may refresh it, then calls
   `_handleVisibilityChange()` — which on a non-browser runtime starts
   auto-refresh whenever `autoRefreshToken` is true, regardless of app state.
   Holding initialization, issuing the background stop, then releasing showed
   the ticker absent after the stop and present after initialization settled.
2. An expired stored session produced a recovery refresh after the background
   stop.
3. Holding a refresh response, stopping auto-refresh, then releasing recorded a
   storage write with `afterStop: true`.

`stopAutoRefresh()` clears the interval and pending timeout that exist at that
moment. It cancels neither initialization nor a refresh already in flight, and
the library exposes no cancellation API for either.

There is a second, independent problem. The failure ADR-005 exists to prevent —
SecureStore rejecting a write while the device is locked — was classified **NOT
RUN** in both REVIEW-019 and REVIEW-020, because no device or simulator
participated and Phase A is offline by design. The property's failure mode
cannot be observed in this phase at all. Two of three fix cycles could have been
spent pursuing something no Phase A evidence could close.

## Decision

**The client never self-schedules a refresh.** `autoRefreshToken: false` at
construction. Refresh is initiated only by explicit, foreground-gated calls from
the session layer.

**A refresh whose persistence fails is surfaced, not silently dropped.** When a
rotated session cannot be written, the session layer treats it as a session it
cannot vouch for and requires re-authentication, rather than continuing against
a token it did not store.

**Locked-device behaviour is NOT RUN and NOT CLAIMED in Phase A.** Phase B
carries a named test requiring a physical device: with a signed-in app
backgrounded and the device locked, force a refresh window and assert that the
write either succeeds or its failure is surfaced. Passing that test is a gate on
Phase B exit.

## Alternatives considered

| Option | Why not |
|---|---|
| Keep `autoRefreshToken: true` and patch the three lifecycle paths | Requires defeating initialization, the visibility handler, and an in-flight refresh in a library offering no cancellation API — three patches against the internal behaviour of a pinned dependency, each of which breaks on upgrade. Attempted in fix cycle 1 and failed on all three probes. |
| Keep ADR-005's clause and treat finding 1 as an implementation defect | The clause asserts a negative this layer cannot enforce and this phase cannot verify. Keeping it guarantees either a permanently open finding or a claim the architecture does not enforce — the exact failure principle 4 exists to prevent. |
| `AFTER_FIRST_UNLOCK` accessibility | Rejected in ADR-005 on at-rest grounds. Unchanged. |
| Adopt auth-js's `lock` option | Rejected in fix cycle 1; REVIEW-020 verified the deprecation premise and judged the call reasonable. `processLock` is deprecated with a `TODO(v3)` removal path, and the property needed here is serialization of adapter operations, which the local queue supplies within its stated scope. |

## Consequences

- **The danger was never that a refresh happened — it was that a rotated token
  vanished and nobody noticed.** Surfacing a failed persist defeats that
  directly. A detected failure can force re-authentication; an undetected one
  trips refresh-token reuse detection days later with no diagnostic trail.
- A long-backgrounded session refreshes on resume; the bootstrap path already
  handles this through `getSession()`.
- Sessions may expire while backgrounded, requiring the user to re-authenticate
  by one-time code. Accepted: an OTP round trip is a lesser harm than a
  silently stranded session, and ADR-004 already priced that round trip in.
- Removing self-scheduling is smaller and more inspectable than the three
  lifecycle patches it replaces. It is enforceable by reading one construction
  option rather than by reasoning about library internals.
