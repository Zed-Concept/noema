# ADR-009: Refresh entrances are not enumerable; persistence failure is

**Date:** 2026-08-26
**Status:** Accepted
**Deciders:** Ahmed (owner); CTRL-005 controller

> Immutable. Once committed, do not edit this file. To change the decision,
> write a new ADR and set this one's status to Superseded.

## Relationship to ADR-007 and ADR-008

**This ADR supersedes ADR-007 in full.** ADR-007's status is set to
`Superseded by ADR-009` — the single edit its own immutability notice sanctions.

Supersession rather than narrowing is deliberate. ADR-008 had already narrowed
ADR-007's surfacing sentence, and this ADR replaces its foreground-gating
clause. With two of three decisions modified, a reader finding ADR-007 marked
`Accepted` would be misled about which of its sentences still bind. Ruling 16's
partial-narrowing mechanic is the right tool once; it is the wrong tool three
times against the same record.

What survives from ADR-007 is restated below rather than left by reference.
ADR-008 remains `Accepted`: its native-only boundary and its reasoning are
correct and carry forward into this record unchanged, and ruling 18 still binds.

## Context

ADR-007 required that refresh be **initiated only by explicit foreground-gated
calls**. Three fix cycles tried to establish that property and each one found a
refresh entrance the previous fix had not accounted for:

- Cycle 1 gated AppState with `stopAutoRefresh`. REVIEW-020 reproduced three
  probes defeating it: initialization restart, recovery refresh, and an
  in-flight refresh writing after the stop.
- Cycle 2 removed self-scheduling with `autoRefreshToken: false`. That
  eliminated probe 1 permanently. REVIEW-021 and REVIEW-021-ADVISORY then found
  probe 2 relocated to the app's own `onAuthStateChange` registration and
  bootstrap `getSession()`.
- Cycle 3 deferred both of those behind `AppState === 'active'`. REVIEW-022
  found that `SupabaseClient` **registers its own auth listener during
  construction**, and that `createClient()` alone issues a token request and
  persists a rotated session with no application auth call. It further found
  that `signOut()` enters `_useSession()` before deletion and so refreshes a
  near-expiry session on the way out. A latent SDK token-provider path is
  recorded as a further entrance.

The manner of that last discovery is itself part of the context. Both prior
reviewers reasoned from reading the pinned source, and both missed the
constructor listener; REVIEW-021-ADVISORY affirmatively stated that
`supabase-js` registers no auth listener, and cycle 3 was built on that
correction. REVIEW-022 ran a probe against the pinned package and got the
opposite answer in one attempt.

The pattern is not three failed attempts at an achievable property. It is
evidence that **enumerating every entrance into a pinned third-party library's
internals is not an architecture.** It is schedule-patching one level up — the
same error the controller instructed the builder to avoid in adapter code at
cycle 2, written into an ADR without noticing.

## Decision

**Refresh entrances are not enumerated and not gated.** Library-internal
refreshes — from construction, from session loading, from `signOut()`, and from
paths not yet identified — are recorded, expected behaviour. No claim is made
anywhere in code, evidence, or documentation that refresh occurs only under
application control.

**`autoRefreshToken: false` stands**, carried forward from ADR-007. It is
retained because REVIEW-022 confirms it permanently eliminated the recurring
ticker, not because it gates entrances.

**The guarantee is persistence, not initiation.** Any rotated session that
cannot be persisted is **detected and forces re-authentication, durably across
process restart**. Detection sits at the write rather than at the initiator,
which is what makes it indifferent to how many entrances exist — the property
REVIEW-021-ADVISORY identified as the mechanism's real strength. Three
requirements follow, and each is a review-gated property:

1. Purge success is **observed, never inferred**. The absence of a removal
  rejection is not proof of deletion; a rejection occurring before removal is
  attempted must not be classified as success.
2. The re-authentication demand is **durable across process restart**. A
  process-local flag does not satisfy this.
3. Rejected refresh Deferreds on this path are handled, not left unhandled.

**Native-only, per ADR-008 and ruling 18.** On web, storage is `localStorage`
and no observer exists; web surfacing remains deferred and unclaimed.

**Locked-device behaviour remains NOT RUN and NOT CLAIMED** in Phase A, carried
forward from ADR-007. The named physical-device test still gates Phase B exit.

## Alternatives considered

| Option | Why not |
|---|---|
| A fourth cycle enumerating the constructor listener and `signOut()` | Three cycles produced three fixes and four-plus entrances, with the newest found only because a reviewer ran a probe instead of reading. A pinned dependency can add an entrance on any upgrade, so the property would need re-establishing on every bump. The gating approach has no stable stopping point. |
| Fork or vendor the client to control initiation | Puts a forked auth library on the highest-risk path in the repo, for a property that persistence detection already covers without it. |
| Keep ADR-007's clause and merge with it open | Leaves a binding record asserting a property the architecture does not enforce — the failure principle 4 exists to prevent, and the same one ADR-006 and ADR-008 were written to correct. |
| Narrow ADR-007 again rather than supersede | The third amendment to one record. Ruling 16's mechanic stops being legible when the surviving sentences must be reconstructed from three later documents. |

## Consequences

- **REVIEW-022 findings 1 and 2 are reclassified as recorded library behaviour,
  not defects.** Finding 3 remains genuinely open and is the sole subject of the
  owner override authorising Unit D's merge. It is recorded in Known Issues and
  closes in a named follow-up unit before Phase B exit.
- **This is the last re-scope of Unit D.** If the follow-up unit does not close
  finding 3, it ships as a Known Issue and the unit is finished regardless. A
  re-scope that reclassifies findings is legitimate once; twice would be budget
  laundering.
- Claims that construction does not refresh, or that a bounded number of
  app-initiated entrances exist, must be deleted wherever they appear.
- A refresh can rotate a token while the app is backgrounded. That is now
  accepted and recorded rather than defended against, and the persistence
  guarantee is what contains it.
- Future dependency upgrades need not re-establish an entrance inventory. They
  must re-establish that detection still sits at the write.
- This is the client auth surface; every future change to it remains RED lane.
