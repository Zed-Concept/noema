# ADR-002: v1 uses Supabase as the integrated backend, accessed directly via supabase-js and RLS with no ORM

**Date:** 2026-08-17
**Status:** Accepted
**Deciders:** Ahmed

> Immutable. Once committed, do not edit this file. To change the decision,
> write a new ADR and set this one's status to Superseded.

## Context

Noema needs Postgres, authentication, file storage, realtime updates, and vector
search, on an Expo client that targets iOS, Android, and web from one codebase.
It is being built by a small agent fleet with one human owner who holds all
production credentials and does all merges.

The real constraint is not raw database capability — several options clear that
bar. It is **how much infrastructure the owner has to assemble and then operate
alone**. Every service that is chosen separately is another dashboard, another
key to rotate, another integration seam where auth and data can disagree, and
another thing an agent can get wrong at three in the morning.

The second question was whether to put a typed query builder between the client
and Postgres. Drizzle was the candidate. At the time of this decision Noema has
no schema, no data model, and no API layer — the client talks to the database
directly.

## Decision

Noema v1 uses **Supabase** as the integrated backend: Postgres with Supabase's own
auth, storage, realtime, and pgvector, rather than assembling equivalent services
from separate providers.

Data access is **`supabase-js` directly against row-level security policies, with
generated TypeScript types**. There is **no ORM in v1** — Drizzle is not adopted.
RLS is the authorization boundary and generated types are the type boundary; no
third layer sits between them. This is revisited if and when Noema grows a
dedicated API layer, at which point a query builder has something to be useful
inside of.

## Alternatives considered

| Option | Why not |
|---|---|
| **Neon + Clerk + R2** — the nearly-chosen option | Each piece is good, and Neon's Postgres branching is genuinely attractive. But it means the owner personally assembles and operates auth, storage, realtime, and vector search across three vendors, and owns every seam between them. Supabase's integration — one auth model that RLS already understands, storage and realtime that speak the same identity — is worth more to a one-owner project than any individual component upgrade. |
| **Drizzle in v1** | With no API layer, Drizzle would sit between the client and RLS, duplicating the type safety that generated Supabase types already provide while adding a schema definition that can drift from the migrations that are actually applied. It solves a problem Noema does not have yet. Revisit if a dedicated API layer appears. |
| Self-hosted Postgres plus hand-rolled auth | Strictly more operational surface for one owner, with authentication as the thing most expensive to get wrong. Not seriously considered. |

## Consequences

Noema is coupled to Supabase in v1, and that coupling is deliberate rather than
incidental — auth, storage, realtime, and RLS are used as an integrated whole, so
migrating away later would not be a database swap. That cost is accepted in
exchange for a backend one person can actually operate.

Authorization lives in the database. Every access rule is an RLS policy, which
makes policies the highest-risk artifact in the repo: they are RED lane in
`AGENTS.md` and they mandatorily trigger advisory review under
[ADR-001](ADR-001-operating-model.md).

Generated types are load-bearing. Because nothing else enforces the shape of the
data, the generated types must be regenerated whenever the schema changes and
committed alongside the migration — a stale type file is a silent correctness
hole, not an inconvenience.

Choosing no ORM keeps queries close to Postgres, which means query construction
is a place where agents can write something subtly wrong and typed only by
generated row shapes. Reviews of data-access code should read the SQL semantics,
not just the types.

This decision is recorded as **binding ruling #2** in
`docs/01-state/PROJECT-STATE.md` in the same commit. Nothing here decides the
schema, the migration workflow, or the policy set — all three remain
`TODO(owner)` in `docs/00-master/ARCHITECTURE.md`.
